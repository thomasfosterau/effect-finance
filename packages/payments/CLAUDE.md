# @thomasfosterau/effect-payments

The vendor-neutral core. Peer: `effect` only. No HTTP code, no vendor SDK, no provider vocabulary.

## Boundary

Imports nothing from this workspace (`.fallowrc.json` zone `core`, no outbound rule). Every provider imports it through its published `exports` (so through `dist/`).

## Invariants

- **Amounts are minor units everywhere in the core.** Major-unit conversion (PayPal decimal strings, Airwallex decimals) happens inside the provider.
- **A new enumeration is lenient from the start.** Declare `Known<Name> = Schema.Literals([...])`, export `<Name> = Enumeration.lenient(Known<Name>)`, and have every provider produce `Other` for a value it cannot map; never add a closed `Schema.Literals` to an entity field a provider fills from a response. Request-only inputs (a filter, `CheckoutMode`) stay closed.
- **Hosted sessions never take an amount.** `CheckoutSession.create` names price ids; what the buyer pays is the provider's price. Both hosted capabilities return an entity whose `url` is required, so a provider answering without one fails rather than inventing a redirect.
- **`idempotencyKey` only where every implementing provider can honour it.** It is on `Customer.create`, `Product.create`, `Price.create`, `PaymentIntent.create` / `confirm`, `Subscription.create`, `Refund.create` and `CheckoutSession.create`, and deliberately not on updates (set-semantics), `Subscription.cancel` / `PaymentIntent.cancel` (PayPal cannot honour a key there) or `BillingPortal.create`; `tests/IdempotencyKey.test.ts` pins that at the type level. A provider maps it to its vendor mechanism and never accepts a key it would silently drop; it calls `IdempotencyKey.validate` first, so a raw string fails with `PaymentInvalidRequestError` before any request. A new create / confirm operation gets the option only after checking every provider that implements it. The replay window is a documentation contract ("a few hours"), not a type: PayPal's Orders API, behind `PaymentIntent.create` / `confirm`, keeps a key for only 6 hours by default. PayPal's limits come from its OpenAPI specifications and fit the 64-character shape (the core README's "Retrying a write safely" has the table); Stripe's and Airwallex's limits and windows are unverified (#93).
- **Adding a capability** means a new module here, a new `exports` entry, and an implementation or an explicit unsupported failure in every provider. A new capability also gets a constructor in `Stub.ts` and a place in `Stub.layer`. A provider without the capability exports a stub layer (built with `Stub`) failing with `PaymentInvalidRequestError` ("<Provider> does not support …", the same failure as an unsupported operation) and leaves it out of its `capabilities` bundle, so the gap still shows at compile time by default.
- **`./internal` is the one semver-exempt subpath.** `src/internal.ts` (`@thomasfosterau/effect-payments/internal`, a single `exports` entry) holds what the providers share because they may import only this package: `shareLogin` and the vendor-neutral integer money core (`exponentFrom`, `scaleToMinor`, `parseDecimal`, `decimalText`, `formatDecimal`, `checkMinorUnits`). It is documented as internal in the README and in its doc comments, and no application imports it. Everything in it takes a fraction-digit count or a plain callback; the per-currency exponent tables and the wire adapters (PayPal's decimal strings, Airwallex's JSON numbers) stay in each provider. A helper two providers duplicate moves here; one a single provider uses stays there. `tests/internal.test.ts` is the only suite for these helpers.
- **One login at a time, and a 401 forgets the token.** `shareLogin(cached, login)` (`internal.ts`) builds a provider's `getToken`: the first caller without a usable token runs the login and publishes its outcome through a `Deferred`, and callers arriving meanwhile await that same outcome (token or error, #65). The slot is cleared before the outcome is published, so the next call after a failure logs in afresh, and if the caller running the login is interrupted the waiters retry rather than being stranded. A login that fails on its own is shared, never retried by its waiters. The 401 half is the provider's: a 401 on a resource request clears the cached token, only if it is still the token that request used, so the next call logs in again.
- **Every exchange is time-boxed.** A provider bounds its login by `loginTimeout` and each resource request by `timeout`, both covering the response body too. A timeout interrupts the fetch (aborting it) and fails with `PaymentNetworkError`; for the login, every caller waiting on it fails with that same error after one `loginTimeout` instead of stalling behind a hung handshake (#54, #65). `timeout` excludes token acquisition. A timed-out non-GET has an unknown outcome, which a caller makes safe to retry with the provider's request id. A timeout is positive and finite, or `Infinity` for none; anything else is a `PaymentConfigError` from `make`. The defaults are the provider's.

## Terms

- **Capability** — one `Context.Service` per resource family (`Customers`, `Products`, `Prices`, `PaymentIntents`, `Subscriptions`, `Refunds`, `CheckoutSessions`, `BillingPortalSessions`), with module-level accessors (`Customer.create`, …). A provider supplies a `Layer` per capability; a program depends only on the capabilities it uses, so a provider may implement a subset (PayPal has no `Customers`).
- **Neutral entity** — a `Schema.Class` (`Customer`, `Product`, `Price`, …) in camelCase with amounts in **minor units** (`Money.amount` in cents for USD). A provider maps its own shape onto it.
- **Lenient enumeration** — every neutral status or type (`PaymentStatus`, `SubscriptionStatus`, `RefundStatus`, `PriceType`, `RecurringInterval`) is `Known | Other` (`Enumeration.ts`): the known literals stay bare strings (`"succeeded"`), and `Other` is the one shared tagged catch-all `{ _tag: "Other", raw: string }` for a provider value the library does not model. Each enumeration exports its literals as `Known<Name>` (the type to use for request filters and params, which can only name a known value) and the lenient union as `<Name>` (the type of the entity field). A provider decoder never fails on an unrecognised enumeration value, and one such value never fails a list page: Stripe's wire schemas use `Enumeration.fromWire(Known<Name>)`, and PayPal / Airwallex map their own spellings with a `to*Status` that returns `Enumeration.other(raw)` in its `default` branch. An exhaustive match over an entity field must handle `Other` with `Enumeration.isOther` (a bare `value._tag` check does not type-check against the plain-string known members).
- **Page** — `Page<A>`, the one pagination shape (`data`, `hasMore`; the next page is requested with a `startingAfter` cursor on the list params); `Deleted` for `del` results.
- **Error channel** — `PaymentsError`, the union of the `Schema.TaggedError` classes in `PaymentsError.ts` (`PaymentProviderError`, `PaymentAuthenticationError`, `PaymentRateLimitError`, `PaymentInvalidRequestError`, `PaymentNetworkError`, `PaymentsUnavailable`, plus `PaymentConfigError` and `SignatureVerificationError`, which are outside the union). Every capability method fails with it and nothing else.
- **"Not configured ≡ down"** — `PaymentsUnavailable`: no provider can serve the call, typically because its credential is absent. Raised at call time, never while a layer is built, so an application without payments configured still starts; it looks to the program exactly like a provider outage (an HTTP API answers it with a 503).
- **Idempotency key** — `IdempotencyKey.ts`: a branded `Schema` (1 to 64 characters of `A-Za-z0-9_-`), `generate`, `validate`; the caller-facing contract (one key per logical write, which errors to retry) is that module's doc comment and the README's "Retrying a write safely".
- **Stub** — `Stub.ts`: capability layers whose every call fails with one given `Effect` (`Stub.layer`, one constructor per capability, `Stub.unavailable`). Providers build their unsupported-capability layers from it.
