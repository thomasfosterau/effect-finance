- [#59](https://github.com/thomasfosterau/effect-finance/pull/59) [`ffa5cc6`](https://github.com/thomasfosterau/effect-finance/commit/ffa5cc646a0e162b00403ef83534ce2e2f3a7b22) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Hosted checkout and billing portal capabilities.

  - **Core:** two new capabilities, each a new subpath. `CheckoutSession` (`CheckoutSessions` service, `CheckoutSession.create`) creates a hosted checkout page. Its `CreateParams` is a union keyed on `mode`: `PaymentParams` (`mode: "payment"`) or `SubscriptionParams` (`mode: "subscription"`, which alone accepts `subscriptionMetadata`, stored on the subscription the checkout creates). Both take an optional `customer`, a non-empty `lineItems` tuple of price ids (quantity defaults to 1; no amount is ever an input), `successUrl`, `cancelUrl` and optional `metadata`. `BillingPortal` (`BillingPortalSessions` service, `BillingPortal.create`) creates a hosted self-service billing page for a `customer` with a `returnUrl`. Both return an entity with `id` and a required `url` to redirect to.
  - **Stripe:** `StripePayments.checkoutSessionsLayer` (`POST /v1/checkout/sessions`; `subscriptionMetadata` becomes `subscription_data[metadata]`) and `StripePayments.billingPortalSessionsLayer` (`POST /v1/billing_portal/sessions`), both included in `capabilities`, `layer` and `layerFromEnv`. A 2xx without a non-empty `url` fails with `PaymentProviderError`.
  - **PayPal / Airwallex:** `checkoutSessionsLayer` and `billingPortalSessionsLayer` stubs that fail every call with `PaymentInvalidRequestError` ("… does not support …"). They are not part of `capabilities`, so a program that needs a hosted checkout still fails to type-check against these providers unless it opts in to the stubs.

- [#80](https://github.com/thomasfosterau/effect-finance/pull/80) [`466ae56`](https://github.com/thomasfosterau/effect-finance/commit/466ae567c5e3f6012b4ab19044277c98943038bb) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Lenient decoding of provider enumerations: a status or type value the neutral model does not cover never fails a whole object or list page, and never collapses silently onto a neutral fallback. It decodes to `Other` carrying the exact raw string the provider sent.

  - **Core:** a new `Enumeration` subpath (`@thomasfosterau/effect-payments/Enumeration`, also `Enumeration` from the root) with the shared catch-all `Other` (`{ _tag: "Other", raw: string }`), `other(raw)`, `isOther`, `lenient`, `parse` and `fromWire`. `PaymentStatus`, `SubscriptionStatus`, `RefundStatus`, `Price.type` (`PriceType`) and `RecurringInterval` are `Known | Other`; the known literals are bare strings, exported as `KnownPaymentStatus`, `KnownSubscriptionStatus`, `KnownRefundStatus`, `KnownPriceType` and `KnownRecurringInterval`.
  - **Matching:** an exhaustive match over a status, price type or interval (`Match.exhaustive`, a `switch` with a `never` default, a `Record<PaymentStatus, …>`) needs a case for `Other` with `Enumeration.isOther(status)` (a bare `status._tag` check does not type-check, since the known members are plain strings). Comparing against a known literal (`status === "succeeded"`) works as usual. Request inputs that name a value (`Subscription.ListParams.status`, `Price.CreateParams.recurring.interval`) take the `Known*` type, since only a known value can be requested.
  - **Stripe:** payment intent `status`, subscription `status`, refund `status`, price `type` and recurring `interval` decode leniently, so one unrecognised value never fails the call or its list page.
  - **PayPal / Airwallex:** an unrecognised order, subscription or refund status (and PayPal billing interval unit) becomes `Other` rather than a neutral fallback.

- [#87](https://github.com/thomasfosterau/effect-finance/pull/87) [`9bbb1ad`](https://github.com/thomasfosterau/effect-finance/commit/9bbb1ad8b8e3f1b07823132edc48b628dddf4f63) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - A neutral, branded `idempotencyKey` on the create and confirm operations, so a caller's retry of a timed-out write is one logical write on every provider (closes [#55](https://github.com/thomasfosterau/effect-finance/issues/55) and [#66](https://github.com/thomasfosterau/effect-finance/issues/66)).

  - **Core.** New `IdempotencyKey` module (`@thomasfosterau/effect-payments/IdempotencyKey`, also exported from the barrel): a branded `Schema` for a key of 1 to 64 characters from `A-Z a-z 0-9 _ -`, `IdempotencyKey.generate` (a random UUID, as an `Effect`) and `IdempotencyKey.validate`. The optional `idempotencyKey?: IdempotencyKey` is added to `Customer.CreateParams`, `Product.CreateParams`, `Price.CreateParams`, `PaymentIntent.CreateParams` / `ConfirmParams`, `Subscription.CreateParams`, `Refund.CreateParams` and `CheckoutSession.CreateParams` (every create / confirm that each provider implementing it can honour). It is not on updates, `Subscription.cancel`, `PaymentIntent.cancel` or `BillingPortal.create`. The key is optional.
  - **Stripe, PayPal, Airwallex.** Each maps the key onto its vendor mechanism: `Idempotency-Key`, `PayPal-Request-Id`, and the body's `request_id` (in place of the fresh per-call id). A key that is not a valid `IdempotencyKey` (a raw string from untyped code) fails with `PaymentInvalidRequestError` before anything is sent.
  - **The pattern.** Create one key per logical write before the first attempt and reuse it on every retry; retry only when the outcome is unknown or the write was not applied (`PaymentNetworkError`, `PaymentProviderError` with `statusCode >= 500`, `PaymentRateLimitError`). A key reused with different parameters is a `PaymentProviderError` on Stripe (`StripeIdempotencyError`); PayPal's and Airwallex's behaviour is unverified. See "Retrying a write safely" in the core README.
  - Stripe's and Airwallex's key-length limits and replay windows could not be checked against their documentation and are documented as unverified (PayPal's: see its own entry).

- [`179f187`](https://github.com/thomasfosterau/effect-finance/commit/179f187f49464204b4b1cc09e344c7ca98a088ac) Thanks [@claude](https://github.com/claude)! - `Page` gains an optional `nextCursor`, the cursor of the next page. It is present when `hasMore` is set. To list the next page, pass it as the list params' `startingAfter`, with the same `limit` and filters. The cursor is opaque: only the provider that returned it reads it.

  - Stripe sets `nextCursor` to the last item's id, which is its own `starting_after`. Passing any item id as `startingAfter` keeps working there.
  - The core's semver-exempt `./internal` subpath gains `pageNumberedList`, which page-numbered providers use to encode and read back their cursors.

- [#61](https://github.com/thomasfosterau/effect-finance/pull/61) [`735ca01`](https://github.com/thomasfosterau/effect-finance/commit/735ca010b3f4177e5ea573a716492f5b0c653ecd) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - "Not configured ≡ down": a Stripe layer that builds without a key and fails each call with a typed `PaymentsUnavailable` while the key is absent.

  - **Core:** a new `PaymentsUnavailable` error (`message`, optional `provider`): no provider can serve the call, typically because its credential is not configured. It is raised at call time, never while a layer is built, and it is part of the `PaymentsError` union, so an exhaustive matcher (`Match.exhaustive`, `Effect.catchTags` covering every tag, a `switch` on `_tag` with a `never` default) handles it.
  - **Core:** a new `Stub` subpath (`@thomasfosterau/effect-payments/Stub`): capability layers whose every call fails with one given `Effect` — `Stub.layer(failure)` for every capability, one constructor per capability (`Stub.customers`, …, `Stub.checkoutSessions`, `Stub.billingPortalSessions`), and `Stub.unavailable(provider?)`, every capability failing with `PaymentsUnavailable`. Building a stub never fails and requires nothing.
  - **Stripe:** `StripePayments.layerConfig(options?)` and `StripeHttp.layerConfig(options?)`. The key is read as a `Redacted` from a configuration variable (`STRIPE_API_KEY` by default, `envVar` to change it) through the current `ConfigProvider` on every call, never at layer construction, so the layer's error type is `never` and a Worker without billing configured still boots. While the key is absent (or empty, or unreadable) every call — every neutral capability, and every raw resource module over `StripeHttp.layerConfig` — fails with `PaymentsUnavailable` (`provider: "stripe"`) before anything is sent; once it is present, calls go to Stripe with that key. The other client options (`apiVersion`, `maxNetworkRetries`, `timeout`, `stripeAccount`, `baseUrl`, `uploadsBaseUrl`) are accepted as in `layer`. `layer` / `layerFromEnv` still fail the build without a key.
  - **PayPal / Airwallex:** the unsupported `checkoutSessionsLayer` / `billingPortalSessionsLayer` stubs are built with the core's `Stub`.

- [#101](https://github.com/thomasfosterau/effect-finance/pull/101) [`c83fdee`](https://github.com/thomasfosterau/effect-finance/commit/c83fdeef93f1457053eb9d06d10ef2d5a47706b2) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `@thomasfosterau/effect-payments/internal`, a documented subpath that is internal and exempt from semver, holding the helpers the Stripe, PayPal and Airwallex providers share. It is not public API and application code should not import it. It holds:

  - `shareLogin`, one in-flight token login shared by every waiting caller;
  - the vendor-neutral integer money core (`exponentFrom`, `scaleToMinor`, `parseDecimal`, `decimalText`, `formatDecimal`, `checkMinorUnits`);
  - the token-login plumbing of an OAuth-style provider (`tokenCache`, `send`, `networkError`, `timedOut`, `timeoutOf`, `isAbsoluteHttpUrl`, `isOk`);
  - the request helpers of a provider built over a generated operation client (`omitUndefined`, `checkId`, `stringField`, `observeResponses`, `rejectedError`);
  - the response handling of a REST provider (`responseDecoder`, `epochSecondsOf`, and `errorFromStatus`, which classifies an HTTP error status onto the neutral error channel).

  None of them names a vendor or a client library. The Stripe, PayPal and Airwallex providers import these helpers from it rather than carrying copies of their own.

- [#34](https://github.com/thomasfosterau/effect-finance/pull/34) [`04c8ab6`](https://github.com/thomasfosterau/effect-finance/commit/04c8ab6c7cf772279a80c09fd448c5035c1f8b1d) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - First release of the `@thomasfosterau/effect-payments` family: a vendor-neutral payments core for Effect 4 and its provider implementations. A program is written against the core's capabilities and runs on any provider by changing only the layer it provides — the payments analogue of Effect's AI modules.

  - **`@thomasfosterau/effect-payments`** — the vendor-neutral core: provider-agnostic capabilities (`Customers`, `Products`, `Prices`, `PaymentIntents`, `Subscriptions`, `Refunds`) as `Context.Service` classes with module-level accessors (`Customer.create`, …), neutral domain entities (`Customer`, `Product`, `Price`, `PaymentIntent`, `Subscription`, `Refund`, `Money`) and a neutral error channel (`PaymentsError`) of `Schema.TaggedError` classes, so errors work with `catchTag` and `instanceof` and are schema-encodable.
  - **`@thomasfosterau/effect-payments-stripe`** — the Stripe implementation: `Layer`s that implement the neutral capabilities over Distilled's Stripe operations (`@distilled.cloud/stripe`), plus a Stripe-specific resource module per Stripe API resource as a provider escape hatch.
  - **`@thomasfosterau/effect-payments-paypal`** and **`@thomasfosterau/effect-payments-airwallex`** — the PayPal (over Distilled's PayPal operations, `@distilled.cloud/paypal`) and Airwallex implementations of the capabilities each vendor supports.
  - **Effect 4.** The core and the Airwallex provider require `effect` `>=4.0.0-rc.118` as a peer; the Stripe and PayPal providers require `^4.0.0`, the peer range of the Distilled packages they depend on. The emitted declarations name the rc.118 module paths (`effect/http`, not `effect/unstable/http`). Code that provides the HTTP client imports `FetchHttpClient` from `effect/http`.
  - **HTTP through `effect/http`.** Every provider's layers require an `HttpClient`: provide `FetchHttpClient.layer`, and stub `FetchHttpClient.Fetch` or the `HttpClient` in tests. Token and error responses are decoded, so a malformed token response fails with `PaymentProviderError`.
  - **Configuration through `Config`.** `layerFromEnv` reads through `Config`, so a custom `ConfigProvider` applies, and a missing or empty variable fails with `PaymentConfigError`. Effect's `ConfigProvider` reads a literal empty string as a missing value.
  - **Endpoint selection.** PayPal's and Airwallex's `layerFromEnv` require `PAYPAL_ENV` / `AIRWALLEX_ENV` (`live` | `sandbox`) to select the endpoint, so neither selects live by default ([#90](https://github.com/thomasfosterau/effect-finance/issues/90)). On PayPal and Airwallex, a configured `baseUrl` that is blank or not an absolute http(s) URL fails with `PaymentConfigError`.
  - **Request caching.** The Stripe resource modules do not cache `retrieve` or `list`; a consumer that wants caching adds it per resolver (`RequestResolver.withCache`) or with `Cache`.
  - The Stripe SDK client the `Webhook.constructEvent*` verifier runs on is provided as `Webhook.StripeService`, whose context key is `"@effect-payments-stripe/StripeService"`.
