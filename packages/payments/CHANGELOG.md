# @thomasfosterau/effect-payments

## 0.1.0

### Minor Changes

- [#59](https://github.com/thomasfosterau/effect-stripe/pull/59) [`ffa5cc6`](https://github.com/thomasfosterau/effect-stripe/commit/ffa5cc646a0e162b00403ef83534ce2e2f3a7b22) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Hosted checkout and billing portal capabilities.

  - **Core:** two new capabilities, each a new subpath. `CheckoutSession` (`CheckoutSessions` service, `CheckoutSession.create`) creates a hosted checkout page. Its `CreateParams` is a union keyed on `mode`: `PaymentParams` (`mode: "payment"`) or `SubscriptionParams` (`mode: "subscription"`, which alone accepts `subscriptionMetadata`, stored on the subscription the checkout creates). Both take an optional `customer`, a non-empty `lineItems` tuple of price ids (quantity defaults to 1; no amount is ever an input), `successUrl`, `cancelUrl` and optional `metadata`. `BillingPortal` (`BillingPortalSessions` service, `BillingPortal.create`) creates a hosted self-service billing page for a `customer` with a `returnUrl`. Both return an entity with `id` and a required `url` to redirect to.
  - **Stripe:** `StripePayments.checkoutSessionsLayer` (`POST /v1/checkout/sessions`; `subscriptionMetadata` becomes `subscription_data[metadata]`) and `StripePayments.billingPortalSessionsLayer` (`POST /v1/billing_portal/sessions`), both included in `capabilities`, `layer` and `layerFromEnv`. A 2xx without a non-empty `url` fails with `PaymentProviderError`.
  - **PayPal / Airwallex:** `checkoutSessionsLayer` and `billingPortalSessionsLayer` stubs that fail every call with `PaymentInvalidRequestError` ("… does not support …"). They are not part of `capabilities`, so a program that needs a hosted checkout still fails to type-check against these providers unless it opts in to the stubs.

- [#80](https://github.com/thomasfosterau/effect-stripe/pull/80) [`466ae56`](https://github.com/thomasfosterau/effect-stripe/commit/466ae567c5e3f6012b4ab19044277c98943038bb) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Lenient decoding of provider enumerations: a status or type value the neutral model does not cover never fails a whole object or list page, and never collapses silently onto a neutral fallback. It decodes to `Other` carrying the exact raw string the provider sent.

  - **Core:** a new `Enumeration` subpath (`@thomasfosterau/effect-payments/Enumeration`, also `Enumeration` from the root) with the shared catch-all `Other` (`{ _tag: "Other", raw: string }`), `other(raw)`, `isOther`, `lenient`, `parse` and `fromWire`. `PaymentStatus`, `SubscriptionStatus`, `RefundStatus`, `Price.type` (`PriceType`) and `RecurringInterval` are `Known | Other`; the known literals are bare strings, exported as `KnownPaymentStatus`, `KnownSubscriptionStatus`, `KnownRefundStatus`, `KnownPriceType` and `KnownRecurringInterval`.
  - **Matching:** an exhaustive match over a status, price type or interval (`Match.exhaustive`, a `switch` with a `never` default, a `Record<PaymentStatus, …>`) needs a case for `Other` with `Enumeration.isOther(status)` (a bare `status._tag` check does not type-check, since the known members are plain strings). Comparing against a known literal (`status === "succeeded"`) works as usual. Request inputs that name a value (`Subscription.ListParams.status`, `Price.CreateParams.recurring.interval`) take the `Known*` type, since only a known value can be requested.
  - **Stripe:** payment intent `status`, subscription `status`, refund `status`, price `type` and recurring `interval` decode leniently, so one unrecognised value never fails the call or its list page.
  - **PayPal / Airwallex:** an unrecognised order, subscription or refund status (and PayPal billing interval unit) becomes `Other` rather than a neutral fallback.

- [#87](https://github.com/thomasfosterau/effect-stripe/pull/87) [`9bbb1ad`](https://github.com/thomasfosterau/effect-stripe/commit/9bbb1ad8b8e3f1b07823132edc48b628dddf4f63) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - A neutral, branded `idempotencyKey` on the create and confirm operations, so a caller's retry of a timed-out write is one logical write on every provider (closes [#55](https://github.com/thomasfosterau/effect-stripe/issues/55) and [#66](https://github.com/thomasfosterau/effect-stripe/issues/66)).

  - **Core.** New `IdempotencyKey` module (`@thomasfosterau/effect-payments/IdempotencyKey`, also exported from the barrel): a branded `Schema` for a key of 1 to 64 characters from `A-Z a-z 0-9 _ -`, `IdempotencyKey.generate` (a random UUID, as an `Effect`) and `IdempotencyKey.validate`. The optional `idempotencyKey?: IdempotencyKey` is added to `Customer.CreateParams`, `Product.CreateParams`, `Price.CreateParams`, `PaymentIntent.CreateParams` / `ConfirmParams`, `Subscription.CreateParams`, `Refund.CreateParams` and `CheckoutSession.CreateParams` (every create / confirm that each provider implementing it can honour). It is not on updates, `Subscription.cancel`, `PaymentIntent.cancel` or `BillingPortal.create`. Additive: a call without a key behaves as before.
  - **Stripe, PayPal, Airwallex.** Each maps the key onto its vendor mechanism: `Idempotency-Key`, `PayPal-Request-Id`, and the body's `request_id` (in place of the fresh per-call id). A key that is not a valid `IdempotencyKey` (a raw string from untyped code) fails with `PaymentInvalidRequestError` before anything is sent.
  - **The pattern.** Create one key per logical write before the first attempt and reuse it on every retry; retry only when the outcome is unknown or the write was not applied (`PaymentNetworkError`, `PaymentProviderError` with `statusCode >= 500`, `PaymentRateLimitError`). A key reused with different parameters is a `PaymentProviderError` on Stripe (`StripeIdempotencyError`); PayPal's and Airwallex's behaviour is unverified. See "Retrying a write safely" in the core README.
  - The vendors' key-length limits and replay windows could not be checked against their documentation and are documented as unverified.

- [#61](https://github.com/thomasfosterau/effect-stripe/pull/61) [`735ca01`](https://github.com/thomasfosterau/effect-stripe/commit/735ca010b3f4177e5ea573a716492f5b0c653ecd) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - "Not configured ≡ down": a Stripe layer that builds without a key and fails each call with a typed `PaymentsUnavailable` while the key is absent.

  - **Core:** a new `PaymentsUnavailable` error (`message`, optional `provider`): no provider can serve the call, typically because its credential is not configured. It is raised at call time, never while a layer is built, and it is part of the `PaymentsError` union, so an exhaustive matcher (`Match.exhaustive`, `Effect.catchTags` covering every tag, a `switch` on `_tag` with a `never` default) handles it.
  - **Core:** a new `Stub` subpath (`@thomasfosterau/effect-payments/Stub`): capability layers whose every call fails with one given `Effect` — `Stub.layer(failure)` for every capability, one constructor per capability (`Stub.customers`, …, `Stub.checkoutSessions`, `Stub.billingPortalSessions`), and `Stub.unavailable(provider?)`, every capability failing with `PaymentsUnavailable`. Building a stub never fails and requires nothing.
  - **Stripe:** `StripePayments.layerConfig(options?)` and `StripeHttp.layerConfig(options?)`. The key is read as a `Redacted` from a configuration variable (`STRIPE_API_KEY` by default, `envVar` to change it) through the current `ConfigProvider` on every call, never at layer construction, so the layer's error type is `never` and a Worker without billing configured still boots. While the key is absent (or empty, or unreadable) every call — every neutral capability, and every raw resource module over `StripeHttp.layerConfig` — fails with `PaymentsUnavailable` (`provider: "stripe"`) before anything is sent; once it is present, calls go over the fetch transport. The other transport options (`apiVersion`, `maxNetworkRetries`, `timeout`, `stripeAccount`, `baseUrl`, `uploadsBaseUrl`) are accepted as in `layer`. `layer` / `layerFromEnv` still fail the build without a key.
  - **PayPal / Airwallex:** the unsupported `checkoutSessionsLayer` / `billingPortalSessionsLayer` stubs are built with the core's `Stub`.

- [#34](https://github.com/thomasfosterau/effect-stripe/pull/34) [`04c8ab6`](https://github.com/thomasfosterau/effect-stripe/commit/04c8ab6c7cf772279a80c09fd448c5035c1f8b1d) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - First release of the `@thomasfosterau/effect-payments` family: a vendor-neutral payments core for Effect 4 and its provider implementations. A program is written against the core's capabilities and runs on any provider by changing only the layer it provides — the payments analogue of Effect's AI modules.

  - **`@thomasfosterau/effect-payments`** — the vendor-neutral core: provider-agnostic capabilities (`Customers`, `Products`, `Prices`, `PaymentIntents`, `Subscriptions`, `Refunds`) as `Context.Service` classes with module-level accessors (`Customer.create`, …), neutral domain entities (`Customer`, `Product`, `Price`, `PaymentIntent`, `Subscription`, `Refund`, `Money`) and a neutral error channel (`PaymentsError`) of `Schema.TaggedError` classes, so errors work with `catchTag` and `instanceof` and are schema-encodable.
  - **`@thomasfosterau/effect-payments-stripe`** — the Stripe implementation: `Layer`s that implement the neutral capabilities, plus the full set of Stripe-specific resource modules as a provider escape hatch.
  - **Effect 4.** Every package requires `effect` `>=4.0.0-rc.118` as a peer; the emitted declarations name the rc.118 module paths (`effect/http`, not `effect/unstable/http`). Code that provides the HTTP client imports `FetchHttpClient` from `effect/http`.
  - **HTTP through `effect/http`.** The PayPal and Airwallex layers, and the Stripe fetch transport, require an `HttpClient`: provide `FetchHttpClient.layer`, and stub `FetchHttpClient.Fetch` or the `HttpClient` in tests. Token and error responses are decoded, so a malformed token response fails with `PaymentProviderError`.
  - **Configuration through `Config`.** `layerFromEnv` reads through `Config`, so a custom `ConfigProvider` applies, and a missing or empty variable fails with `PaymentConfigError`. Effect's `ConfigProvider` reads a literal empty string as a missing value.
  - **An empty or unset `PAYPAL_BASE_URL` / `AIRWALLEX_BASE_URL` selects the live endpoint.** There is no sandbox/live switch yet ([#90](https://github.com/thomasfosterau/effect-stripe/issues/90)): a sandbox deployment must set the sandbox URL explicitly (`https://api-m.sandbox.paypal.com`, `https://api-demo.airwallex.com`). `make` refuses a `baseUrl` that is blank or not an absolute http(s) URL with `PaymentConfigError`.
  - **Request caching.** The Stripe resource modules do not cache `retrieve` or `list`; a consumer that wants caching adds it per resolver (`RequestResolver.withCache`) or with `Cache`.
  - `StripeService`'s context key is `"@effect-payments-stripe/StripeService"`.
  - The generated Stripe schemas are produced with `@effect/openapi-generator` at the same Effect version.

- [#62](https://github.com/thomasfosterau/effect-stripe/pull/62) [`d33de87`](https://github.com/thomasfosterau/effect-stripe/commit/d33de870d6c8960095ef82a828abb961ad37f08f) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Follow-ups to the "not configured ≡ down" `layerConfig` ([#42](https://github.com/thomasfosterau/effect-stripe/issues/42)).

  - **Stripe:** `StripeHttp.layerConfig` / `StripePayments.layerConfig` now read the key from the calling fiber's `ConfigProvider` first and fall back to the `ConfigProvider` the layer was built under, so a provider attached to the layer (`layerConfig().pipe(Layer.provide(ConfigProvider.layer(…)))`) is honoured, as it is for `layerFromEnv`. Before, such a provider was ignored and every call failed with `PaymentsUnavailable`. The `PaymentsUnavailable` message now says the variable "is not set or is empty"; an unreadable variable is logged at debug level (its name only) before being treated as absent; the call, including the unavailable path, runs in a `StripeHttp.layerConfig.request` span; and each failure is a fresh error instance.
  - **Core:** `Stub.Failure` (the type of the failure a stub's calls run) is exported, and `Stub.unavailable` constructs a fresh `PaymentsUnavailable` per call.
