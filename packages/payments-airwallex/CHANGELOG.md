### Patch Changes

- [#73](https://github.com/thomasfosterau/effect-finance/pull/73) [`55712f2`](https://github.com/thomasfosterau/effect-finance/commit/55712f22360de5076daccd629533b1241d9b555d) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Convert money with integer arithmetic, never float multiplication.

  - **Response amounts.** A response amount is read from the shortest decimal form of the double `JSON.parse` produced (exponent notation included). It fails with `PaymentProviderError`, never silently rounded, in three cases:
    - it has more decimals than its currency allows (e.g. `10.005` USD);
    - it is beyond the safe-integer range in minor units;
    - its double is ambiguous, because a different amount (or one with excess decimals) parses to the same double. For two-decimal currencies this affects some amounts at or above 2^45 major units, e.g. `45035996273704.95` USD.

    Guarantee: an accepted amount is the wire value rounded to the nearest minor unit, and exact when the wire text has at most `exponent` decimals. Excess digits are not always caught: `10721136062241.369` shares a double with `.37` and is accepted as `.37`, and digits finer than a double can resolve (e.g. `0.30000000000000001`) cannot be detected. Rejection starts at about 2^45 major units for two-decimal currencies, 2^42 for three-decimal ones and 2^52 (even integers) for zero-decimal ones.

  - **Request amounts.** A request amount (a payment intent's or a partial refund's `amount`) fails with `PaymentInvalidRequestError` before anything is sent when it is negative, not a safe integer, or has no JSON number carrying it exactly. A partial refund checks its amount before looking up the payment intent's currency.

- [#63](https://github.com/thomasfosterau/effect-finance/pull/63) [`0b1c2f2`](https://github.com/thomasfosterau/effect-finance/commit/0b1c2f27a2dec5690cde06a4227bc80ec73f9329) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Time-box every request the PayPal and Airwallex providers make.

  - **The token login has a timeout** (`loginTimeout` on `PayPalConfig` / `AirwallexConfig`, in milliseconds, default 30 000), so a login the vendor accepted but never answers cannot stall the requests waiting for a token. A login that runs out of time is aborted and fails with `PaymentNetworkError`, and the next caller logs in afresh.

- [#53](https://github.com/thomasfosterau/effect-finance/pull/53) [`dc4e803`](https://github.com/thomasfosterau/effect-finance/commit/dc4e803829aeb6a2d45481ebadcf0ff9d45f2628) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Token and header handling in the PayPal and Airwallex providers:

  - Every request sends `Content-Type: application/json`, body or not. PayPal answers a bodyless POST without it, such as `/v1/billing/plans/{id}/activate` (the `Prices.update` activate/deactivate path), with 415; Airwallex gets the same header for consistency.
  - Only one login is in flight at a time. Concurrent first requests, and requests racing a token refresh, await that login and get its token, or all fail with its very error (for example the `PaymentNetworkError` of a login timeout) after one `loginTimeout`. A failure is not cached: the next call after it starts a fresh login. If the caller running the login is interrupted, the login is aborted, and the waiting callers try again.
  - A 401 from the vendor clears the cached token, but only if it is still the token that request used, so the next request logs in again. A late 401 for a token another request has already replaced leaves the new token in place.
