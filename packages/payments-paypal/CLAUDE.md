# @thomasfosterau/effect-payments-paypal

PayPal REST: `Products`, `Prices` (billing plans), `PaymentIntents` (orders), `Subscriptions` and `Refunds`. Peer: `effect`. Dependency: the core. No vendor SDK. Requires `HttpClient` (`effect/http`).

## Boundary

Imports only `@thomasfosterau/effect-payments` from this workspace (`.fallowrc.json` zone `paypal`, allow `core`).

## Invariants

- **Every call goes through `HttpClient`**, never `globalThis.fetch`: the layers require `HttpClient.HttpClient`, so a consumer provides `FetchHttpClient.layer` and a test stubs `FetchHttpClient.Fetch`. Every body is decoded with `Schema`: token and error bodies in the client, resource bodies in the capability layers — `request` returns `unknown`, and each layer pipes it through a `decode*` from `internal/mapping.ts` (a wire `Schema` narrowed to the fields the mapping reads), so a 2xx that does not decode fails with `PaymentProviderError`. Statuses decode as strings; the `to*Status` functions map a recognised one onto the neutral literal and an unrecognised one onto `Enumeration.Other` carrying the raw string (never a silent neutral fallback, never a decode failure).
- **Login sharing and timeouts:** see `packages/payments/CLAUDE.md` (`shareLogin`, "One login at a time", "Every exchange is time-boxed"). Provider-specific: `getToken` is `shareLogin(cachedToken, login)`; a 401 on a resource request clears the cached token, only if it is still the token that request used; `loginTimeout` defaults to 30 s and `timeout` to 80 s (the Stripe transport's per-attempt default); a caller makes a timed-out non-GET safe to retry with `PayPalRequest.requestId` (below).
- **`requestId` is the `PayPal-Request-Id` header, `POST` only.** One id per logical write, created before the first attempt and reused by every retry (the client never generates or retries one itself). An empty id, or one on a non-`POST`, fails with `PaymentInvalidRequestError` before anything is sent: a header PayPal ignores would leave the caller believing a retry is safe. Length (about 108) and retention are unverified (#93). The capability layers pass the neutral `idempotencyKey` of a create / confirm through `IdempotencyKey.validate` into `requestId`; with no key none is sent (a random one would deduplicate nothing, since a caller's retry re-runs the layer).
- **`Content-Type: application/json` on every request**, body or not (PayPal answers a bodyless POST without it with 415).
- **Configuration from the environment is read through `Config`** in `layerFromEnv`, and a missing or empty variable still fails with `PaymentConfigError`. Effect rc.118's `ConfigProvider` treats a literal empty string as a missing value, so an empty variable is the same as an unset one: an empty id or secret fails with `PaymentConfigError`, and an empty `PAYPAL_BASE_URL` falls back to the `PAYPAL_ENV` endpoint. A provider built with `preserveEmptyStrings: true` restores the old reading, which is the safer one for `PAYPAL_BASE_URL`: a blank stays `""` and `make` refuses it with `PaymentConfigError` (a `baseUrl` must be an absolute http(s) URL), instead of silently selecting an environment's endpoint.
- **`PAYPAL_ENV` is required** (`live` | `sandbox`, read with `Config.Literals`): `layerFromEnv` never selects live by default (#90). It maps onto `PayPalConfig.environment` (`live` → `https://api-m.paypal.com`, `sandbox` → `https://api-m.sandbox.paypal.com`); `baseUrl` / `PAYPAL_BASE_URL`, when set, wins. In `make` / `layer`, `environment` is optional and defaults to `live`.
- **No `Customers`.** PayPal has no first-class customer resource; the provider deliberately implements a subset of the core's capabilities, and a program needing `Customers` fails to type-check against this layer.
- **Money crosses the boundary as major-unit decimal strings** (`internal/money.ts`); the core stays in minor units. Conversion is integer arithmetic, never a float, and the per-currency exponent follows PayPal's currency-codes reference (HUF, JPY, TWD zero-decimal), not Stripe's list. The response decoders reject an amount with excess decimals rather than round it. Request amounts must be non-negative safe integers and fail with `PaymentInvalidRequestError` before any request.
- **Vendor error bodies become neutral errors in `internal/error.ts`.** The client secret and the bearer token never appear in one: the client secret is `Redacted<string>` in the config (read with `Config.Redacted` in `layerFromEnv`) and unwrapped only where the login request is built, and a transport failure keeps only the underlying cause — never the `HttpClientError`, whose request carries the credential headers.

## Terms

- **Client** — `PayPalClient` (`PayPal.ts`): an OAuth client-credentials handshake whose access token is cached in a `Ref` and refreshed a minute before expiry, plus one `request` function every capability goes through. `PayPal.layer` / `layerFromEnv` (`PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, required `PAYPAL_ENV`, optional `PAYPAL_BASE_URL` override).
- **Capability layers** — `PayPalPayments.*Layer`, `capabilities`, `layer` / `layerFromEnv`.
