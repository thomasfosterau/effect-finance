- [#83](https://github.com/thomasfosterau/effect-stripe/pull/83) [`41040a9`](https://github.com/thomasfosterau/effect-stripe/commit/41040a9d853dc52f1f81aeb6d7da2c808e67e802) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Per-call idempotency keys at each provider's request layer, so a caller's retry of a timed-out write can be recognised by the vendor ([#55](https://github.com/thomasfosterau/effect-stripe/issues/55), part of [#66](https://github.com/thomasfosterau/effect-stripe/issues/66)).

  - **Stripe.** Every resource-module operation takes a trailing `options?: { idempotencyKey?, stripeAccount? }` (`StripeHttp.RequestOptions`, also exported as `RequestOptions`), forwarded to the transport as `Idempotency-Key` and `Stripe-Account`. The change is additive. Create one key per logical write and reuse it on every retry. An empty `idempotencyKey` or `stripeAccount` fails with `PaymentInvalidRequestError` before anything is sent.
    - **Point-free use.** The trailing parameter means an operation passed point-free to an iterator that supplies an index now binds the index to `options` and fails to type-check, e.g. `Effect.forEach(ids, Customer.del)` (TS2769). Wrap it: `(id) => Customer.del(id)`. No change of semver level.
  - **PayPal.** `PayPalRequest.requestId` is sent as the `PayPal-Request-Id` header on a `POST`.
  - **Airwallex.** `AirwallexRequest.requestId` is written into the body as `request_id`, replacing the fresh id the capability layers generate.
  - An empty `requestId`, or one on a method that cannot honour it, fails with `PaymentInvalidRequestError` before anything is sent, rather than being silently dropped.
  - The vendors' key-length limits and replay windows could not be checked against their documentation and are documented as unverified.

- [#80](https://github.com/thomasfosterau/effect-stripe/pull/80) [`466ae56`](https://github.com/thomasfosterau/effect-stripe/commit/466ae567c5e3f6012b4ab19044277c98943038bb) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Lenient decoding of provider enumerations: a status or type value the neutral model does not cover never fails a whole object or list page, and never collapses silently onto a neutral fallback. It decodes to `Other` carrying the exact raw string the provider sent.

  - **Core:** a new `Enumeration` subpath (`@thomasfosterau/effect-payments/Enumeration`, also `Enumeration` from the root) with the shared catch-all `Other` (`{ _tag: "Other", raw: string }`), `other(raw)`, `isOther`, `lenient`, `parse` and `fromWire`. `PaymentStatus`, `SubscriptionStatus`, `RefundStatus`, `Price.type` (`PriceType`) and `RecurringInterval` are `Known | Other`; the known literals are bare strings, exported as `KnownPaymentStatus`, `KnownSubscriptionStatus`, `KnownRefundStatus`, `KnownPriceType` and `KnownRecurringInterval`.
  - **Matching:** an exhaustive match over a status, price type or interval (`Match.exhaustive`, a `switch` with a `never` default, a `Record<PaymentStatus, …>`) needs a case for `Other` with `Enumeration.isOther(status)` (a bare `status._tag` check does not type-check, since the known members are plain strings).   - **Stripe:** payment intent `status`, subscription `status`, refund `status`, price `type` and recurring `interval` decode leniently, so one unrecognised value never fails the call or its list page.
  - **PayPal / Airwallex:** an unrecognised order, subscription or refund status (and PayPal billing interval unit) becomes `Other` rather than a neutral fallback.

- [#87](https://github.com/thomasfosterau/effect-stripe/pull/87) [`9bbb1ad`](https://github.com/thomasfosterau/effect-stripe/commit/9bbb1ad8b8e3f1b07823132edc48b628dddf4f63) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - A neutral, branded `idempotencyKey` on the create and confirm operations, so a caller's retry of a timed-out write is one logical write on every provider (closes [#55](https://github.com/thomasfosterau/effect-stripe/issues/55) and [#66](https://github.com/thomasfosterau/effect-stripe/issues/66)).

  - **Core.** New `IdempotencyKey` module (`@thomasfosterau/effect-payments/IdempotencyKey`, also exported from the barrel): a branded `Schema` for a key of 1 to 64 characters from `A-Z a-z 0-9 _ -`, `IdempotencyKey.generate` (a random UUID, as an `Effect`) and `IdempotencyKey.validate`. The optional `idempotencyKey?: IdempotencyKey` is added to `Customer.CreateParams`, `Product.CreateParams`, `Price.CreateParams`, `PaymentIntent.CreateParams` / `ConfirmParams`, `Subscription.CreateParams`, `Refund.CreateParams` and `CheckoutSession.CreateParams` (every create / confirm that each provider implementing it can honour). It is not on updates, `Subscription.cancel`, `PaymentIntent.cancel` or `BillingPortal.create`. Additive: a call without a key behaves as before.

- [#61](https://github.com/thomasfosterau/effect-stripe/pull/61) [`735ca01`](https://github.com/thomasfosterau/effect-stripe/commit/735ca010b3f4177e5ea573a716492f5b0c653ecd) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - "Not configured ≡ down": a Stripe layer that builds without a key and fails each call with a typed `PaymentsUnavailable` while the key is absent.

  - **Core:** a new `PaymentsUnavailable` error (`message`, optional `provider`): no provider can serve the call, typically because its credential is not configured. It is raised at call time, never while a layer is built, and it is part of the `PaymentsError` union, so an exhaustive matcher (`Match.exhaustive`, `Effect.catchTags` covering every tag, a `switch` on `_tag` with a `never` default) handles it.
  - **Core:** a new `Stub` subpath (`@thomasfosterau/effect-payments/Stub`): capability layers whose every call fails with one given `Effect` — `Stub.layer(failure)` for every capability, one constructor per capability (`Stub.customers`, …, `Stub.checkoutSessions`, `Stub.billingPortalSessions`), and `Stub.unavailable(provider?)`, every capability failing with `PaymentsUnavailable`. Building a stub never fails and requires nothing.
  - **Stripe:** `StripePayments.layerConfig(options?)` and `StripeHttp.layerConfig(options?)`. The key is read as a `Redacted` from a configuration variable (`STRIPE_API_KEY` by default, `envVar` to change it) through the current `ConfigProvider` on every call, never at layer construction, so the layer's error type is `never` and a Worker without billing configured still boots. While the key is absent (or empty, or unreadable) every call — every neutral capability, and every raw resource module over `StripeHttp.layerConfig` — fails with `PaymentsUnavailable` (`provider: "stripe"`) before anything is sent; once it is present, calls go over the fetch transport. The other transport options (`apiVersion`, `maxNetworkRetries`, `timeout`, `stripeAccount`, `baseUrl`, `uploadsBaseUrl`) are accepted as in `layer`. `layer` / `layerFromEnv` still fail the build without a key.
  - **PayPal / Airwallex:** the unsupported `checkoutSessionsLayer` / `billingPortalSessionsLayer` stubs are built with the core's `Stub`.

- [#57](https://github.com/thomasfosterau/effect-stripe/pull/57) [`f9d3730`](https://github.com/thomasfosterau/effect-stripe/commit/f9d3730b48da88b4b475451fd53ed9c0bd9cc2cc) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - The Stripe provider runs on a fetch-only transport, and the `stripe` SDK is an optional peer.

  - **`StripeHttp` transport** (`@thomasfosterau/effect-payments-stripe/StripeHttp`) over `effect/http`'s `HttpClient`, with no Node API and no SDK, so it runs in a Cloudflare Worker. It form-encodes parameters the way the SDK does (`metadata[key]`, `items[0][price]`), pins `Stripe-Version` (`DEFAULT_API_VERSION` unless `apiVersion` is set), sends the key as a `Redacted` bearer token, refuses redirects, and retries connection failures, `409`s and `5xx`s with the SDK's backoff and `Stripe-Should-Retry` handling. Each `POST` that may be retried gets one generated `Idempotency-Key` for all of its attempts. Stripe's error envelope is decoded with `Schema` onto the neutral errors: authentication → `PaymentAuthenticationError`, rate limit → `PaymentRateLimitError` (with `Retry-After`), invalid request → `PaymentInvalidRequestError` (with `param`), connection → `PaymentNetworkError`, anything else → `PaymentProviderError`.
  - **Resource modules** (`Customer`, `Treasury.FinancialAccount`, …) require `StripeHttp`, and take and return the `stripe` package's types. `Terminal.Location` and `Terminal.Reader` `retrieve` / `update` return the SDK's `T | DeletedT` union, because Stripe answers a deleted object with its `{ deleted: true }` stub.
  - **`StripePayments.layer` / `layerFromEnv`** run on the fetch transport and require an `HttpClient`, as the PayPal and Airwallex layers do: provide `FetchHttpClient.layer`. `StripePayments.layer` takes a `StripeHttpConfig` (`apiKey`, `apiVersion`, `maxNetworkRetries`, `timeout`, `stripeAccount`, `baseUrl`, `uploadsBaseUrl`); `appInfo` exists only on the SDK transport's `StripeConfig`, because the fetch transport sends no SDK user agent. `StripePayments.capabilities` and the individual capability layers require `StripeHttp`. Every response they read is decoded with `Schema`, so a malformed 2xx fails with `PaymentProviderError`. Subscriptions read the billing period from the first item when the API version puts it there (2025-03-31 "basil" and later), and otherwise from the subscription.
  - **Errors keep Stripe's details.** Error fields Stripe sends as `null` (such as `"code": null`) are read as absent, so the error is still classified by its `type`. A `PaymentProviderError`'s `cause` is Stripe's whole error object as received, including `decline_code`, `payment_intent`, `advice_code` and the rest.
  - **A missing or empty id fails.** A resource-module or capability call with an empty (or, from untyped code, non-string) id fails with `PaymentInvalidRequestError` and sends no request, rather than addressing the list endpoint.
  - **API keys are `Redacted`.** `StripeHttpConfig.apiKey` and `StripeConfig.apiKey` are `Redacted<string>`, and `layerFromEnv` reads the key with `Config.Redacted`.
  - **The SDK is an optional alternative.** `stripe` is an optional peer dependency. The `Stripe` module (`@thomasfosterau/effect-payments-stripe/Stripe`) is the SDK transport: `Stripe.layer` / `layerFromEnv` provide the SDK client (`StripeService`) and `StripeHttp` over `stripe.rawRequest`. It is the only module that loads `stripe` at runtime, and it is not re-exported from the package root, which exports `StripeHttp` and the `StripeHttpConfig` type. Install `stripe` (as a dev dependency) for the resource modules' types, and at runtime for `Stripe.layer` or the SDK-based `Webhook.constructEvent*` verifier.

- [#60](https://github.com/thomasfosterau/effect-stripe/pull/60) [`df5aa7b`](https://github.com/thomasfosterau/effect-stripe/commit/df5aa7be99148b0e103cc6d8c79990103405f21c) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `Webhook.verify` is the default webhook verifier: a Workers-safe WebCrypto implementation that needs neither the `stripe` SDK nor any Node API ([#41](https://github.com/thomasfosterau/effect-stripe/issues/41)).

  - **`Webhook.verify({ payload, header, secret, tolerance? })`** checks the `Stripe-Signature` header (HMAC-SHA256 over `${t}.${rawBody}`, every `v1` digest compared in constant time, so secret rotation works), refuses a timestamp more than `tolerance` seconds either side of now (default `DEFAULT_TOLERANCE`, 300 s; "now" comes from Effect's `Clock`), and then decodes the event envelope. The secret is a `Redacted<string>`; the payload is the raw body — canonically its bytes (`new Uint8Array(await request.arrayBuffer())`), or a string as a lossy convenience. `tolerance: 0` means "the same second" here (the SDK's `constructEvent` reads it as "no check"); an unusable tolerance or an empty secret refuses the delivery. A refusal is a `SignatureVerificationError` whose `message` is one of the exported constants (`MALFORMED_HEADER_MESSAGE`, `OUTSIDE_TOLERANCE_MESSAGE`, `SIGNATURE_MISMATCH_MESSAGE`, `INVALID_TOLERANCE_MESSAGE`, `SIGNATURE_UNAVAILABLE_MESSAGE`) and which never carries the secret or the payload; nothing is decoded until the signature verifies, and a signed body that is not an event fails with `Schema.SchemaError`.
  - **`Webhook.verifySignature`** (the check alone), **`Webhook.signatureHeader`** (sign a payload as Stripe does, without the SDK — for tests and tooling only) and **`Webhook.SIGNATURE_HEADER`**.
  - **Lenient event decoders**: `WebhookEvent` / `decodeEvent`, `handledEventTypes` / `isHandledEventType`, `HandledEvent` / `decodeHandledEvent` (a `type`-discriminated union, `none` for unhandled types), and `CheckoutSessionObject`, `SubscriptionObject`, `InvoiceObject` with `decodeCheckoutSession`, `decodeSubscription`, `decodeInvoice`. `InvoiceObject` decodes the subscription from both the legacy top-level `subscription` and `parent.subscription_details.subscription` (API `2025-03-31.basil` and later); `invoiceSubscription` reads it, preferring the newer location.

  The SDK-based `Webhook.constructEvent` / `constructEventAsync` / `generateTestHeaderString*` remain available as the optional alternative (they need `Stripe.layer` and the `stripe` peer).
