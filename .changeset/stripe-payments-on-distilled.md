`StripePayments` runs on Distilled's Stripe operations (`@distilled.cloud/stripe`) instead of this package's own `StripeHttp` transport (#146).

- **New dependencies.** `@distilled.cloud/stripe` and `@distilled.cloud/core`, both pinned to `1.0.0-rc.13` (about 30 MB installed, with core's `graphql` dependency). A bundler keeps only the operations the capabilities you use call: a bundle of `customersLayer` alone grows from about 18 KB to 63 KB minified (5 KB to 20 KB gzipped), and one of every capability from about 23 KB to 178 KB (7 KB to 43 KB gzipped), with `effect` external.
- **Breaking: the `effect` peer floor rises from `>=4.0.0-rc.118` to `^4.0.0`.** Distilled declares the peer `effect: ^4.0.0`, which no `4.0.0-rc.*` prerelease satisfies, so this package now requires the same. The core and the other providers keep `>=4.0.0-rc.118`.
- **Breaking: the capabilities need a `process` global.** Distilled reads `process.env.DISTILLED_DEBUG_HTTP`, unguarded, on every request and response, so without a `process` global every capability call dies with a defect. On Cloudflare Workers, enable the `nodejs_compat` compatibility flag. Building the layers does not need it, and a `layerConfig` call made while the key is unset still fails with `PaymentsUnavailable` before Distilled runs. `StripeHttp`, the raw resource modules and `Webhook.verify` do not need it either. Leave `DISTILLED_DEBUG_HTTP` unset outside local debugging: while it is set, Distilled logs every request's method and URL and the first 400 characters of every request and response body to `console.error`, which can include part or all of a `client_secret`. It does not log the `Authorization` header.
- **Breaking: what the capability layers require.** `customersLayer` … `billingPortalSessionsLayer` and `capabilities` now require Distilled's `Credentials` (from `@distilled.cloud/stripe/Credentials`) and an `HttpClient`, where they required `StripeHttp`. Provide `Credentials.credentials({ apiKey })` (which means depending on `@distilled.cloud/stripe` yourself, at exactly this package's version of it) and `FetchHttpClient.layer`, or use `layer` / `layerFromEnv` / `layerConfig`, whose signatures are unchanged. The capabilities no longer run over a `StripeHttp` you provide, so the `stripe` SDK transport (`Stripe.layer`) no longer backs them; it still backs the raw resource modules.
- **Breaking: the capabilities move to Stripe API version `2026-07-29.dahlia`.** The capability layers now pin `Stripe-Version` on every request (retries included) to `StripePayments.DISTILLED_API_VERSION`, the API version the pinned `@distilled.cloud/stripe` release's schemas are generated from, instead of `DEFAULT_API_VERSION` (`2025-08-27.basil`). It follows Distilled: a later release that moves the Distilled pin moves this version too, and says so in its changelog. An explicit `apiVersion` passed to `layer` or `layerConfig` still wins. The raw resource modules, `StripeHttp` and the `Stripe` SDK transport keep `DEFAULT_API_VERSION` (`2025-08-27.basil`) for now, so the two halves of the package send different versions. Stripe delivers webhook events at the receiving endpoint's API version, so create the endpoints whose events you read beside the capabilities at `2026-07-29.dahlia`, and move any code of yours that reads Stripe's JSON directly (event payloads, your own calls) to the same version. The fields the capabilities map are unchanged in that version.
- **Unchanged behaviour.** The SDK's retry policy, the per-attempt timeout, refused redirects, the generated `Idempotency-Key` shared by a retryable `POST`'s attempts, the neutral error mapping (401 / 403 / 429 from the status, the whole vendor error object as the cause) and the decoding of the fields each capability maps all carry over. `uploadsBaseUrl` is ignored, since no capability uploads. Distilled's own response validation stays lenient for these calls even under its `ResponseValidation.strict`, so a response is never refused over a field the capabilities do not read.
- **Id check.** A path id that is not a non-empty string now fails with `PaymentInvalidRequestError` (`The customer id must be a non-empty string`, `param: "id"`) before anything is sent, where it named the path segment.
- `StripeHttp`, the `Stripe` SDK transport, the raw resource modules and the generated schemas are unchanged.
