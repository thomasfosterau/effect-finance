`PayPalPayments` runs on Distilled's PayPal operations (`@distilled.cloud/paypal`), and the package publishes no PayPal REST client of its own (#146).

- **Dependencies.** `@distilled.cloud/paypal` and `@distilled.cloud/core`, both pinned exactly to `1.0.0-rc.15`, the same version as the Stripe package's (about 9 MB installed, with core's `graphql` dependency). A bundler keeps only the capabilities you use: a bundle of `productsLayer` alone is about 40 KB minified (14 KB gzipped), and one of every capability about 117 KB (27 KB gzipped), with `effect` external.
- **The `effect` peer is `^4.0.0`.** Distilled declares the peer `effect: ^4.0.0`, which no `4.0.0-rc.*` prerelease satisfies, so this package requires the same, as the Stripe package does. The core and the Airwallex provider accept `>=4.0.0-rc.118`.
- **The capabilities need a `process` global.** Distilled reads `process.env.DISTILLED_DEBUG_HTTP`, unguarded, on every request and response, so without a `process` global every capability call dies with a defect. On Cloudflare Workers, enable the `nodejs_compat` compatibility flag. Building the layers and the OAuth login do not need it. While `DISTILLED_DEBUG_HTTP` is set, Distilled logs each request's method and path template and each response's status to `console.error`, and nothing else.
- **Layers.** `PayPalPayments.layer(config)` / `layerFromEnv()` log in with OAuth client credentials (one shared, time-boxed login; the token refreshed a minute before it expires and forgotten after a 401) at the endpoint `PAYPAL_ENV` / `environment` select, or `PAYPAL_BASE_URL` / `baseUrl`, and need an `HttpClient`. `PayPalConfig` and `PayPalEnvironment` are exported from `./PayPalPayments`, and as types from the package root. The individual capability layers (`productsLayer` … `refundsLayer`) and `capabilities` require Distilled's `Credentials` (from `@distilled.cloud/paypal/Credentials`: an access token, as a `Redacted<string>`, and base URL, e.g. `fromApiKey({ apiKey: Redacted.make(token), apiBaseUrl })`) and an `HttpClient`, and send that token as it is, with no login or refresh; providing `Credentials` yourself means depending on `@distilled.cloud/paypal` at exactly this package's version of it.
- **Request policy.** `Content-Type` and `Accept: application/json` on every request (PayPal answers a bodyless `POST` without one with 415). The neutral `idempotencyKey` is sent as `PayPal-Request-Id` on six writes (order create and capture, product, plan and subscription create, capture refund) and nowhere else. Nothing is retried, each request times out after `timeout` (80 s by default), and every failure maps onto the neutral `PaymentsError` channel from the response's status and PayPal's error body; no Distilled error class reaches a caller. Distilled's response validation is lenient, even under its `ResponseValidation.strict`, so a response is never refused over a field the capabilities do not read; the fields they map are decoded.
- **Id and item checks.** A path id that is not a non-empty string fails with `PaymentInvalidRequestError` (`The product id must be a non-empty string`, `param: "id"`) before anything is sent, and so does `Subscription.create` without an item (`param: "items"`).
- **Calls the capabilities do not cover.** Use `@distilled.cloud/paypal`'s operations directly, with an access token of your own in its `Credentials`, at exactly this package's version of it. Its failures are Distilled's error classes rather than `PaymentsError`, it retries 5xx and 429 responses by default, and its input types declare optional members as bare `?: T`, so under `exactOptionalPropertyTypes` omit an absent member rather than pass `undefined`.
