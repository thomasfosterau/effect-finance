`PayPalPayments` runs on Distilled's PayPal operations (`@distilled.cloud/paypal`) instead of this package's own `PayPalClient` (#146).

- **New dependencies.** `@distilled.cloud/paypal` and `@distilled.cloud/core`, both pinned to `1.0.0-rc.13`, the same version as the Stripe package's (about 9 MB installed, with core's `graphql` dependency). A bundler now keeps only the capabilities you use: a bundle of `productsLayer` alone is about 40 KB minified (14 KB gzipped), and one of every capability about 117 KB (27 KB gzipped), with `effect` external, where before any import kept all of them at about 19 KB (6 KB gzipped).
- **Breaking: the `effect` peer floor rises from `>=4.0.0-rc.118` to `^4.0.0`.** Distilled declares the peer `effect: ^4.0.0`, which no `4.0.0-rc.*` prerelease satisfies, so this package now requires the same, as the Stripe package does. The core and the Airwallex provider keep `>=4.0.0-rc.118`.
- **Breaking: the capabilities need a `process` global.** Distilled reads `process.env.DISTILLED_DEBUG_HTTP`, unguarded, on every request and response, so without a `process` global every capability call dies with a defect. On Cloudflare Workers, enable the `nodejs_compat` compatibility flag. Building the layers and the OAuth login do not need it, and neither does `PayPalClient`. While `DISTILLED_DEBUG_HTTP` is set, Distilled logs each request's method and path template and each response's status to `console.error`, and nothing else.
- **Breaking: what the capability layers require.** `productsLayer` … `refundsLayer` and `capabilities` now require Distilled's `Credentials` (from `@distilled.cloud/paypal/Credentials`: an access token and base URL, e.g. `fromApiKey({ apiKey, apiBaseUrl })`) and an `HttpClient`, where they required `PayPalClient`. Over `Credentials` they send that token as it is, with no login or refresh. To log in with client credentials, use `layer` / `layerFromEnv`, whose signatures are unchanged, instead of providing `PayPal.layer(config)` to `capabilities`. Providing your own `Credentials` means depending on `@distilled.cloud/paypal` yourself, at exactly this package's version of it.
- **Unchanged behaviour.** `layer` / `layerFromEnv` log in through the same OAuth client-credentials login and token cache as `PayPalClient` (one shared, time-boxed login; the token refreshed a minute before it expires and forgotten after a 401), at the same endpoint (`PAYPAL_ENV`, `environment`, `PAYPAL_BASE_URL` / `baseUrl`). The requests are the same: the paths, query strings and bodies, `Content-Type` and `Accept: application/json` on every request, and the neutral `idempotencyKey` as `PayPal-Request-Id` on the same six writes and nowhere else. Nothing is retried, each request times out after `timeout` (80 s by default), and every failure maps onto the same neutral error, from the response's status and PayPal's error body. Distilled's own response validation stays lenient even under its `ResponseValidation.strict`, so a response is never refused over a field the capabilities do not read.
- **Id and item checks.** A path id that is not a non-empty string now fails with `PaymentInvalidRequestError` (`The product id must be a non-empty string`, `param: "id"`) before anything is sent, and so does `Subscription.create` without an item (`param: "items"`), where a request without a plan id used to reach PayPal.
- `PayPalClient` (`./PayPal`) is unchanged; it no longer backs the capability layers.
